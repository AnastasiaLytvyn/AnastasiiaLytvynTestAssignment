# Divorce Online

## Як запустити

**1. Якщо немає, то встановити Node.js** — завантажити з [nodejs.org](https://nodejs.org) (кнопка LTS) і встановити як звичайну програму.

**2. Завантажити репозиторій** — на сторінці GitHub натиснути `Code → Download ZIP`, розпакувати архів.

**3. Відкрити термінал у папці проєкту**

- Windows: відкрити папку, клікнути правою кнопкою на порожньому місці → "Відкрити в терміналі"
- Mac: перетягнути папку на іконку Terminal у Dock

**4. Виконати по черзі:**

```
npm install
npx playwright install chromium webkit
npx playwright test
```

Після завершення запустити щоб побачити результат у браузері:

```
npx playwright show-report
```

## Що тестується і чому

### Покриті сценарії

1. **CTA-навігація** (`cta-navigation.spec.ts`) перевіряє, що всі кнопки з лендингу, що мають вікдрити квіз - ведуть на квіз, кожна кнопка має окремий тест. Лендинг є єдиною точкою входу у воронку і якщо кнопка зламана, користувач не може почати квіз і конверсія неможлива.
2. **Повна воронка** (`landing-to-registration.spec.ts`) - це хеппі пас, проходить весь шлях користувача від лендингу до успішної реєстрації. Якщо він падає, значить щось зламалось на критичному шляху і жоден новий користувач не може зареєструватись.
3. Валідація форми реєстрації (`registration.spec.ts`) - форма реєстрації є останнім кроком перед тим як користувач стає лідом.  Якщо валідація пропускає некоректні дані - це потрапляє в систему і створює проблеми для подальшої обробки. Тест в собі містить саме негативні кейси, позитивний кейс реєстрації покриває хеппі пас.
4. **Прогрес квізу після reload** (`quiz-progress.spec.ts`) - так як, квіз складається з багатьох кроків і користувач може випадково перезавантажити сторінку, перевіряється, що прогрес не скидується, адже втрата прогресу збільшує шанс що користувач покине квіз і не завершить реєстрацію.


```
Більшість тестів стабільні, але хеппі пас і тести реєстрації можуть іноді давати статус flaky — це означає що тест то проходить, то падає без жодних змін у коді. Причина не в багах продукту, а в тому що тести залежать від реального сайту з Angular-анімаціями і мережевими затримками, які щоразу трохи відрізняються. При повторному запуску такий тест зазвичай проходить.
```

### Що не покрито і чому це можна відкласти

1. **Авторизація через Google** - нестабільна через антибот-захист Google. У майбутньому можна пошукати можливі обходи цього, але доцільність покриття залежить від бізнес-контексту - який відсоток користувачів використовує цей метод.
2. Кроки після реєстрації виходять за межі основної конверсійної метрики. При цьому ці кроки ведуть до оплати, тому також потребують стабільного покриття, але в рамках окремого набору тестів.
3. **Негативні сценарії квізу** - квіз не має складної валідації на рівні UX, більшість кроків не мають обов'язкових полів, валідація введення імені не є критичною на поточному етапі.
4. **Повторна реєстрація з вже існуючим email** - більшість користувачів реєструються вперше, тому спочатку важливо забезпечити стабільність основного шляху. Поведінку при дублікаті email є едж кейсом, що не є критичним.
5. Потрапляння на реєстрацію через Sign In на лендингу - кнопкою більше будуть користуватись користувачі, що вже знайомі з продуктом, але тут треба більше аналітичних даних даного продукту.

## Додаткова підсвітка

1. **Чи точно треба кнопка Continue на питаннях з однією відповіддю?** Юзер обирає варіант і його редіректить автоматично далі. Використовується лише якщо юзер скористається браузерною кнопкою назад, то щоб перейти далі треба вже буде натиснути Continue - це особливості Ангуляра чи це можливо буде обійти?
2. **Різний регістр кнопок на лендингу** - кнопки CTA написані по-різному (Check Eligibility - в секції з бенефітами з малої). Варто привести до єдиного стилю для консистентності UI.
3. Зараз хеппі пас прописаний по першим відповідям - нормальна практика автотестів, але бачу, що наявність/вміст деяких екранів залежать від відповідей, тому покращення автоматизації можливе, коли краще ознайомлюсь зі структурою побудови квізу.
4. Також є сценарій доступу до квізу для вже зареєстрованого і авторизованого користувача - тут треба більше бізнес-контексту, так як використовується декілька доменів і в майбутньому можливі різні типи документів і тд.
5. Нестабільна поява кнопки Continue - в деяких запусках тестів кнопка Continue не з'являлась вчасно або взагалі не з'являлась, в майбутньому треба дослідити це питання для покращення автоматизації і підтвердження, що у юзерів такої проблеми не виникало, тут йде саме вплив Ангуляра.
